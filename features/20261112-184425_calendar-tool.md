# Calendar tool: Mac and Google calendars, read and write

- Status: in progress
- Phase: current
- Origin: Bill, 2026-11-12 ("can we set up read only access to google calendars"; then "letts create a general tool that can use mac or google calendars. lets tive it all the fetures it can have, it doens' tneed to e read only.")
- Created: 2026-11-12 (UTC)
- Started: 2026-11-12, branch `feature-upgrade-feature-tool`

One `calendar` tool, with a backend behind it, the way `reminders` is built. Two backends:

- **Mac**: the Mac's Calendar through EventKit (the framework Reminders already uses). It reaches every account added to macOS: iCloud, Google, Exchange. No keys.
- **Google**: the Google Calendar API directly, signed in once in a browser, the token kept in the Keychain. Needed for the things EventKit can't do (below), and for a Google account that isn't added to the Mac.

## Done when

Reading (both backends):

- [ ] "What's on my calendar today / tomorrow / Friday / this week / next week?" reads the events in order, all-day ones first.
- [ ] "What's next?" and "when is the dentist?" (search by title, forward from now).
- [ ] "Tell me about the dentist appointment": place, notes, who's invited, the link.
- [ ] "Am I free Friday afternoon?" and "when am I free tomorrow?" from the events.
- [ ] "Which calendars do I have?"; a request can name one ("on the family calendar").

Writing (both backends):

- [ ] "Add lunch with Sam Friday at noon" creates an event: title, start, length or end (one hour when not said), all-day, calendar, place, notes, an alert, a repeat (daily, weekly, monthly, yearly, weekdays).
- [ ] "Move the dentist to 3", "make it two hours", "rename it", "change the place": changes an event found by title or by its number in the last listing.
- [ ] "Cancel the dentist appointment" deletes one.
- [ ] A repeating event: asks "just this one, or all of them from now on?" before a change or a delete.
- [ ] A change or a delete that matches several events asks which.

Google backend only (EventKit can't do these):

- [ ] Invite people to an event, and say who has accepted.
- [ ] Answer an invitation: accept, decline, maybe.
- [ ] Add a Google Meet link.

Around it:

- [ ] `calendar:` in `tools.yaml`: the backend, which calendars are reached, the default calendar for new events. `assistant calendar grant`, `calendars`, and (Google) `connect`.
- [ ] A stub with the reason when access is missing, as `reminders` is.
- [ ] Tests against a fake backend; docs (`docs/calendar.md`, README, architecture §8, the runbook's tool kinds); live check by chat on a test calendar, then by voice.

## Blocking decisions

Answered by Bill, 2026-11-12: 1 "Mac first (Recommended)"; 2 "Changes and deletes (Recommended)"; 3 "All, with a skip list (Recommended)"; 4 "Later, separate feature (Recommended)". Decisions 5 and 6 are for the Google backend and are still open.

1. **Which backend first.** Proposal: the Mac backend now. It needs no keys and reaches Google calendars when the Google account is added to the Mac. The Google backend second: it needs an OAuth client that you create in Google Cloud, and a browser sign-in (`assistant calendar connect`) whose token goes to the Keychain.
2. **Asking before a write.** Proposal: adding an event doesn't ask (the reply says what was added, so a mistake is heard). Changing or deleting asks first ("Move Dentist from 2 to 3 on Friday?").
3. **Which calendars.** Proposal: read all of them, except ones named under `calendar.skip` (holidays, birthdays). New events go to the Mac's default calendar unless one is named. Live tests use a `Victoria Test` calendar only.
4. **Spoken alerts before events.** "You have the dentist in 15 minutes" as a notification on the room devices. Proposal: a second feature, after this one.
5. **(Google backend) Inviting people sends them email.** Proposal: always ask before a write that sends an invitation or a cancellation to someone else.
6. **(Google backend) The secret.** The OAuth client's id and secret and the sign-in token are secrets. Proposal: Keychain and `config/.env` only, set by you with `assistant secrets set` and `assistant calendar connect`; never shown to Claude.

## Notes

- macOS gives calendar access as "full access" or "add only". Reading needs full access, so read-only can't be enforced by macOS; only by our code.
- No satellites involved, so this is current-phase work.
- MCP: Google has a remote Calendar MCP server (`https://calendarmcp.googleapis.com/mcp/v1`), in Developer Preview, and there are community ones. Victoria's `mcp` tool kind only talks to Home Assistant, so using one would first need a general MCP client with Google sign-in. Not proposed.

## Evidence and notes

Built 2026-11-12, the Mac backend and the tool:

- `tools/calendars.py`: `CalendarService` (actions `list`, `next`, `find`, `details`, `free`, `calendars`, `add`, `change`, `delete`, and `confirm`, which a yes runs) and `EventKitBackend`. `parse_range` reads the spoken day or stretch; times reuse the reminders tool's reading.
- A change or a delete is held per device for 2 minutes and runs only on a yes from that device. A repeating event asks "just this one, or all of them from now on?" first. Read-only calendars are refused.
- `CalendarConfig` (`calendar:` in `tools.yaml`): `skip`, `default_calendar`, `default_minutes`, `free_from`, `free_until`. The `calendar` tool is in both `tools.yaml` files. On the dev Mac `default_calendar` is `Victoria Test`, which doesn't exist yet.
- `assistant calendar grant`, `calendars`, `new NAME`. Docs: `docs/calendar.md`, architecture §8, README, runbook.
- Tests: `tests/test_calendars.py` (16), against a stand-in. `uv run pytest -q`: 587 passed, 3 skipped.

Found and fixed during these checks:

- The service didn't see a calendar renamed in the Calendar app until a restart ("Untitled" for `Victoria Test`). The store is now reread on every request. Not checked against a change made outside the service since the fix.
- The model put the event's name in `when`, or under a parameter it made up, and added `"when": "today"` nobody said. The tool now takes the name from either place and looks past a day that finds nothing.
- A change or delete waiting for a yes is dropped when another calendar request arrives on that device.

Seen, not fixed (the router model, `google/gemma-4-12b`):

- "Make the Zebra checkpoint two hours long" and "Cancel the Zebra review" went to the timer tool; "Tell me about the Zebra checkpoint event" offered Hermes. Said with "appointment" or "calendar" they reached the calendar tool.
- "What are the details of my … appointment?" used `find` (when it is), not `details`.
- A rename plus a new length in one request was not tried again after the first attempt failed on the made-up parameter.
- A title matches on any shared word: "Zebra review" found "Zebra checkpoint". The question before a change or delete names the event it found.

Tests: `tests/test_calendars.py` (17). `uv run pytest -q`: 588 passed, 3 skipped.
